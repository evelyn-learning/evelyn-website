# GDI tester home: per-learner lesson history with summary, replay and PDF — design

Date: 2026-11-05 (brainstormed with Praveen 11-04 evening PST). Status: draft for builder check.

## Intent and why

GDI (Josh, James) will share the trial lesson with four more colleagues. Each person gets their own learner
account (already minted: `tester-1..4`, `josh`; Praveen's and James's can be minted the same way). After a lesson
they want to see, per person: the level the tutor settled on, the tutor's assessment including pronunciation,
recommendations for further English practice, a replay with audio, and the session PDF. Today the embed page ends on
a bare "Session Complete" card with two counts, and the replay/PDF exist only behind admin-minted links. Josh is not
an admin; each account sees only its own results. The email to GDI will say: five learner accounts, a shared pool of
300 minutes, each login has its own session summary, recording and PDF.

## Goals

- One link per tester, the "home" link. Opening it shows **Your lessons**: every completed session for that learner
  (newest first) with its summary, a *Replay with audio* button and a *Download PDF* button, plus **Start a new lesson**.
  Closing the tab loses nothing; the link is the way back.
- The **end-of-lesson screen** on the embed page shows the same summary for the session just finished, with the same
  two buttons and a link back to Your lessons.
- The **summary** is generated once per session, server-side, at session end, and stored on the session. Sections:
  level (the working level the tutor set, with the evidence line), tutor's assessment (grammar points practised,
  the corrections that came up, pronunciation scores and the weak sounds the tutor named), recommendations (3–5
  concrete practice suggestions). **English first, one short Japanese line under each section.**
- Reuses: the replay page (audio + whiteboard timeline + transcript), the PDF exporter, the embed token, the
  partner secret the engine already resolves per partner.

## Non-goals / anti-goals

- No admin or aggregate view for Josh; no cross-learner page. (Praveen: "no need to make Josh the admin".)
- No login beyond the signed token link; no password, no email verification.
- No new lesson: every session is the Work-projects lesson (second sessions skip the level check, as today).
- Not a general "learner portal" for all partners yet: built partner-agnostic in code, but only the gdi-demo flow is
  minted, styled and tested this round.
- Anti-goal: a summary that invents scores. Every number on the page comes from the session record (pronunciation
  events, level event, correction cards). The model writes prose around them; it never grades.
- Anti-goal: regenerating summaries on every view (cost, drift). Stored once; an explicit admin regenerate only.

## Constraints

- Prod Mongo via the laptop tunnel on :2710; writes only through the engine's own save path.
- Tutor prompts stay generic (no GDI-specific wording in the summary prompt; lesson facts come from the session).
- Typed-turn kill switch and the rest of the engine untouched; the summary call is a separate server-side call with
  the `judge`-class Haiku model from the model registry (cheap; ~2–4k input tokens per session).
- Deploy target: tutor-demo :3009 only (deploy-tutor-demo.sh); :3007/:3008 untouched.
- Links expire with the embed token (30 days as minted today).

## The parts, as decided

### 1. Home page `/tutor-portal/home?token=<embed token>`
- Same token the embed page accepts (payload: partner_id, student_id, student_name, lesson config). Verified with
  `verifyEmbedTokenAsync`; a bad/expired token shows the same refusal the embed page shows.
- Lists `TutorSession` rows where `sourcePartnerId = partner_id`, `studentId = student_id`, `status = completed`,
  newest first. Each row: date/time (local), duration, level badge, the stored summary (collapsed to the level line
  + first recommendation; "Show full summary" expands), *Replay with audio*, *Download PDF*.
- *Replay with audio* opens `/tutor-portal/replay?token=<replay token>` in a new tab. The replay token is signed
  server-side by the engine with the partner's secret (new `signReplayToken` next to `verifyReplayToken`, same payload
  shape, 30-day exp, branding carried from the partner row as the mint script does today).
- *Download PDF* uses the existing `ExportSessionPDFButton` with the stored transcript/commands (same as the replay
  page), so the home page needs no new exporter path.
- **Start a new lesson** links to `/tutor-portal/embed?token=<same token>&return=home` (see 3).
- A learner with no sessions yet sees the lesson title, the tester guide line, and the Start button.
- Branding: partner `branding.product_name`/colour as the replay page does; otherwise the engine default.

### 2. Session summary (`TutorSession.learnerSummary`)
- Generated by the engine when a partner session is saved with `status: completed` (the embed page's save path),
  once; idempotent on sessionId; failures logged, the page shows "Summary not available yet" and a Retry that
  calls the generate endpoint again (no auto-retry loop).
- Inputs (all from the session record): transcript; correction cards (`showSentence` with emphasis = the model
  sentence; the correction pairs from the typed `correction` cards); `working_level_set` debug event (level +
  evidence); `pronunciation_note_planted` events (overall score, prosody, weak words, the practised sentence);
  lessonProgress (parts completed); duration.
- Output JSON stored as-is: `{ level: { value, evidence_en, evidence_ja }, assessment: { grammar_en, grammar_ja,
  corrections: [{ student, corrected }], pronunciation: { practised: [{ sentence, overall, prosody, weak }],
  comment_en, comment_ja } }, recommendations: [{ en, ja }] (3–5), generated_at, model, version: 1 }`.
- Prompt: generic (works for any language lesson): "Write the learner-facing summary of this lesson from the
  facts below; do not invent scores; English first, one short Japanese line per section"; the facts block is built
  by code, not by the model. Temperature low. Output validated against the shape; a malformed reply is one retry.
- Shown on the home page and on the end-of-lesson screen; the PDF is unchanged this round (the summary can be added
  to the PDF later; non-goal now).

### 3. End-of-lesson screen (embed page)
- Replaces the "Session Complete" card for partner sessions: title, the summary (polled from
  `GET /api/tutor-portal/session-summary?token=<embed token>&session=<id>` until generated, up to ~20 s, then the
  Retry state), *Replay with audio*, *Download PDF*, and **Back to your lessons** (`/tutor-portal/home?token=…`).
- When the embed page was opened without `return=home` (a partner's own host page), the back link is omitted and the
  rest stays, so other partners' embeds gain the summary too but keep their own navigation.

### 4. Minting, pool, email (ops, not engine code)
- `mint-demo-links.js trial` gains `--home`: prints home links (same payload, path `/tutor-portal/home`). The five
  tester links in `~/.evelyn/partners/gdi-trial.links.prod.txt` are re-minted as home links; James gets one too.
- Pool: before the email goes out, `partner-pool.sh set gdi-demo <used + 300>` so the "300 minutes" in the email is
  the real remaining balance (Praveen's call at send time; the pool is partner-wide, not per group).
- Email draft to Josh and James: `docs/whitelabel/gdi/email-testers-2026-11-05.md` (English; what each link is,
  mic/browser notes from TESTER-GUIDE.md, the 300-minute pool, that every session is the same lesson, who to contact).

## Left to the builder

- Exact page layout and copy (brand-neutral, phone-width OK); the Japanese lines' wording (natural, polite).
- Where the generate call lives (server action vs. API route) and the polling details on the end screen.
- Which Haiku model id (registry role) and the prompt text; the facts-block format.
- Index on `TutorSession` for `{ sourcePartnerId, studentId, status }` if the query needs it.
- Test shape: pure functions for the facts block and the summary validator; a route pin for token scoping (a token
  for student A never lists student B's sessions); a pin that the summary is generated once per session.

## Calls made after the builder check (mine, not Praveen's — he can overrule any)

1. **Which sessions appear.** Every session of the learner with at least 4 transcript turns, any status (completed,
   ended by the 30-minute cap, abandoned tab), newest first. A session with fewer turns is hidden. Status is shown as
   a small label ("Completed" / "Ended early").
2. **When the summary is generated.** A `generate` endpoint guarded by an atomic `findOneAndUpdate` on
   `learnerSummary.status` (absent → `pending`), so it runs once per session. Called from (a) the end-of-lesson
   screen and (b) the home page on first view of any listed session that has no summary (fire-and-forget; the row
   shows "Preparing your summary…" and the client polls). A closed tab therefore still gets its summary on the next
   visit; the Retry button is for a `failed` status only. One in-call retry on a malformed model reply, no loop.
3. **Resumed sessions.** The stored summary carries the transcript length it was written from; when a session is
   saved again with ≥ 3 more turns, the next generate call rewrites it (version +1). Otherwise once.
4. **Level on second sessions.** When the session has no `working_level_set` event (level check skipped), the level
   comes from the learner's StudentProfile `workingLevel` with the evidence line "set in your lesson on <date>".
   The section is always shown.
5. **Scoping.** Home, summary and replay-token minting refuse an embed token without `student_id`, and every lookup
   matches `sourcePartnerId = token.partner_id` AND `studentId = token.student_id`. The partner save path is
   hardened in the same change: when the request carries an embed token, `studentId`/`sourcePartnerId` are taken
   from the token, not the body. Replay tokens are minted only after that match, 30-day exp.
6. **Audio.** The Replay button is always shown; the replay page already falls back to transcript-only when a
   session has no audio (builder verifies); the label says "Replay with audio" only when `hasAudio`.
7. **Student ids.** `mint-demo-links.js trial --home` re-signs the EXISTING payloads from the links file (same
   student ids, new path), so history survives; a new tester (James) gets a fresh id. Praveen's current id
   (`gdi-trial-praveen-to0i2x`) is kept.
8. **Model.** Registry role `judge` (Haiku), temperature 0.2, JSON output validated by shape.
